# Предлагаемый процесс агентной разработки AssetGen

Дата — 21 ноября 2026 года. Статус — предложение; до решения автора этот документ не заменяет [действующие правила](../AGENTS.md).

## Какие проблемы процесс должен закрывать

- В одном рабочем дереве сейчас смешаны изменения CLI, Blender, схем, документации и большого числа ассетов. Такой объём трудно ревьюить и безопасно продолжать другому агенту.
- Наличие тестовых скриптов ещё не означает обязательную проверку: без CI команду можно не запустить.
- Проверки локального `out/` закономерно пропускают несобранные спеки; это полезно для просмотра, но недопустимо как единственный release gate.
- Задачи на ассет, генератор и рефакторинг имеют разные риски и не должны проходить по одному расплывчатому понятию «готово».
- Отдельные скрипты проверки и новые публичные поля могут размножаться быстрее, чем появляется общий контракт.

Цель процесса — маленькие обратимые изменения с воспроизводимым доказательством, а не увеличение бюрократии ради формальностей.

## 1. Рабочая единица и Git-flow

Рекомендуется **trunk-based flow с короткими task branches**, а не классический GitFlow с долгоживущими `develop`/`release`. Проект имеет один основной конвейер и не нуждается в параллельной поддержке нескольких релизных веток.

### Правила

1. `main` — всегда проходящая обязательные проверки ветка. Прямые коммиты и force-push запрещены настройками Git-хостинга.
2. Одна карточка задачи = одна короткая ветка = один PR. Имена: `feat/asset-assemblies`, `fix/texture-stale-input`, `test/clean-build-gate`, `docs/architecture-audit`.
3. Ветка создаётся от актуального `main`. Долгая смешанная ветка вроде текущей `initial-setup` перед введением процесса разделяется на понятные PR; новые работы не добавляются в неё по умолчанию.
4. Каждый агент работает в отдельном `git worktree` и с отдельным `ASSETGEN_OUT`. Нельзя переключать ветку, делать stash или чистить чужое рабочее дерево.
5. Коммиты атомарные: исправление и его тест идут вместе. Сгенерированный `out/`, `.blend1`, `__pycache__`, временные сцены и логи не коммитятся.
6. В PR используется squash merge для одной задачи, если промежуточные коммиты не представляют самостоятельной ценности. История решений остаётся в карточке, рабочий контракт — в README/схеме/skill.
7. Изменение публичного DSL, схемы отчёта, экспорта или Git/CI-правил требует ревью автора проекта. Агент не утверждает собственный архитектурный PR.

Пример изоляции, выполняемый уже после постановки отдельной задачи:

```powershell
git fetch origin
git worktree add ../model-generator-asset-assemblies -b feat/asset-assemblies origin/main
```

В новом worktree агент сначала повторяет `git status --short --branch`, создаёт/открывает карточку и только затем меняет код. Наличие чужих незакоммиченных файлов в другом worktree не является основанием их копировать или удалять.

### Когда PR нужно разделить

Это триггеры для остановки и пересмотра объёма, а не механические метрики качества:

- меняются два независимых публичных контракта;
- одна ветка одновременно содержит новый ассет, расширение генератора и общий рефакторинг без общей приёмки;
- проверка требует нескольких несвязанных Godot-сценариев;
- diff нельзя описать одним предложением и одним набором тестов;
- исправление по пути обнаружило отдельный дефект — он регистрируется в техдолге/карточке, а не незаметно включается в PR.

## 2. Жизненный цикл задачи агента

### Definition of Ready

До первой правки должны быть известны:

- потребитель и границы;
- входные данные и ожидаемый наблюдаемый результат;
- контрольный ассет/спека;
- команды проверки и версии инструментов;
- связанные карточки и задачи техдолга;
- для бага — ожидалось/наблюдалось и сценарий воспроизведения.

Если художественный критерий нельзя измерить, заранее называются ракурс, свет, дистанция и конкретный признак: например, «волокно идёт вдоль каждой доски на iso и в Godot с 1,5 м», а не «стало красивее».

### Выполнение

1. Воспроизвести дефект или показать минимальной спекой отсутствие возможности.
2. Добавить проверку, которая падает до исправления по нужной причине.
3. Сделать минимальное изменение в одном слое; публичное поле провести через схему → разрешение → сборку → экспорт → тест → документацию.
4. Повторить исходный сценарий и старую спеку без нового поля.
5. Просмотреть собственный diff, незнакомые изменения не включать.
6. Передать PR отдельному reviewer-агенту или человеку. Reviewer получает diff, критерии и результаты, а не вывод автора «всё работает».
7. Закрыть карточку только с фактическими командами, результатами, ограничениями и ссылкой на PR. Не оставлять все карточки бессрочно «в работе».

Автор кода и reviewer не должны быть одним и тем же контекстом агента. Для маленькой документационной правки достаточно человеческого ревью PR.

## 3. Обязательная верифицируемость

### Матрица проверок

| Уровень | Что проверяет | Когда обязателен |
|---|---|---|
| Системный Python | Схемы, defaults, семантические ошибки, digest, выбор стадий, paths | Каждый PR |
| Blender unit/integration | Примитивы, transforms, cutouts, UV, граф материала, bake | При затрагивании соответствующего кода и в общем reference job |
| Чистая сборка | CLI, временный output, полный набор артефактов, lock, stale input, failure recovery | Каждый PR генератора; обязательный контрольный набор |
| GLB contract | JSON glTF, материалы, samplers, textures, иерархия, pivot, collision, triangles | Каждый собранный ассет |
| Godot smoke | Импорт, материал, масштаб, коллизия, открывание/проигрывание при наличии | Для изменений экспорта и игровых контрактов |
| Визуальная приёмка | Закреплённые камера/свет/дистанция, нейтральный mesh и textured result | Для формы и материала; человек утверждает художественное изменение |

### Правила тестов

- Тест обязан падать при удалении/поломке проверяемого поведения. Для исправления сохраняется доказательство красного прогона.
- Явно выбранный обязательный ассет нельзя пропускать из-за отсутствия `out/`. Skip допустим только в отдельном discovery-режиме и должен печатать причину и итоговое число.
- CI печатает `selected / passed / skipped / failed`; для обязательного набора `skipped > 0` означает failure.
- Детерминизм проверяется от исходной спеки, а не только двумя bake из одного `.blend`. Сравнение геометрии нормализует порядок и служебные пути; сравнение изображений учитывает закреплённую версию Blender.
- Не создавать новый почти одинаковый `verify_<asset>.py` для каждого ассета. Общий механизм параметризуется спекой/манифестом; специфичный ray test остаётся маленьким fixture.
- Пиксельный baseline не заменяет структурные проверки GLB и не смешивается с художественным одобрением.
- Тесты не читают и не перезаписывают пользовательский `out/`; используют временный каталог и очищают только его.

### Минимальный контрольный набор

Сейчас базовый набор уже покрывает бочку, колонну, череп, `urn` и окна. Его следует расширять по риску, а не по количеству:

- один joined static prop;
- один `lathe` с цилиндрической UV;
- один cutout с глухой и сквозной полостью;
- один прозрачный материал;
- один assembly с подвижным узлом после появления этапа 1;
- один генераторный представитель флоры с закреплённым seed;
- один персонажный rig после появления этапа 5.

Полный каталог собирается отдельной scheduled/nightly проверкой или по требованию перед релизом. Он не должен маскировать быстрый обязательный PR-набор.

## 4. CI и защита ветки

Предлагаются три независимых job с явными версиями Python, Blender и Godot.

### `pr-fast` — системный Python

```powershell
python -m unittest discover -s tests -p "test_*.py" -v
```

Дополнительно: валидация всех JSON, проверка отсутствия дубликатов имён, локальных ссылок Markdown и недопустимых generated-файлов в diff. Этот job выполняется для каждого PR.

### `pr-blender` — чистые контракты

```powershell
python tests/verify_reference_builds.py
& $env:BLENDER -b --factory-startup --python-exit-code 1 -P tests/verify_texture_pipeline.py -- $PWD
```

Остальные Blender/Godot проверки подключаются по затронутым стадиям либо входят в обязательный набор, пока время прогона остаётся приемлемым. В CI `BLENDER` и `GODOT_BIN` задаются из закреплённой установки, а не из локального `assetgen.config.json`.

### `scheduled-full` — весь каталог

- чистые model+texture для всех обязательных пар спек;
- полный GLB contract и Godot import;
- повторная сборка контрольного набора для детерминизма;
- отчёт по triangles, размерам, UV, material slots, времени и пропускам;
- сохранение превью и отчётов как временных CI artifacts, а не коммит в репозиторий.

Для защиты `main` обязательны `pr-fast`, `pr-blender` и минимум один reviewer. Ручной запуск локальных команд не отмечается как эквивалент CI без прикреплённого результата.

## 5. Контроль роста архитектуры и каталога

### Публичный DSL

Новое поле/оператор принимается только вместе с:

- одним текущим потребителем и минимальной спекой;
- объяснением, почему композиция существующих средств недостаточна;
- default/поведением для старого JSON;
- семантическими ограничениями и понятным путём ошибки до поля;
- тестами сборки и экспорта, README и skill;
- явным non-goal, чтобы следующий агент не расширял оператор бесконечно.

Defaults должны иметь один источник истины или автоматический тест эквивалентности схемы и runtime. Общий helper вводится при реальном втором потребителе; при этом не создаётся абстракция «на будущее» только ради уменьшения строк.

### Каталог

- Исходные `specs/`, templates, palettes и разрешённые исходные текстуры версионируются.
- `out/` является производным; обмен результатами — через CI artifacts или релизный архив с manifest и версиями инструментов.
- Для семейства с общей формой предпочтителен генератор/шаблон, а не десятки почти совпадающих рукописных JSON.
- Новый ассет должен быть связан с очередью, тестовым fixture или явным запросом автора.
- Крупные reference PNG и исходные текстуры требуют проверки размера, происхождения и лицензии; дубли и промежуточные сравнения остаются вне Git.

### Документация

- README описывает текущий контракт; карточка хранит историю задачи; план не используется как скрытая замена документации.
- Прежний аудит не переписывается так, будто замечания всегда были исправлены: рядом фиксируются дата и результат итерации.
- Закрытая карточка содержит исход каждого сообщённого бага и ссылку на PR.
- Техдолг имеет приоритет, evidence, сценарий влияния и приёмку. Запись «отрефакторить файл» без наблюдаемого результата не является задачей.

## 6. Definition of Done

Изменение готово, если:

1. Все критерии карточки подтверждены командой, структурной проверкой или названным визуальным сценарием.
2. Исходный баг воспроизведён до и проверен после тем же способом.
3. Старые спеки и контрольный набор проходят; отличия результата объяснены.
4. Обязательные CI checks зелёные без неучтённых skip.
5. Проверены как минимум два слабых места: старая спека, отсутствующий bake, другой pivot, collision, прозрачность, mipmaps или неуспешный Blender — по риску изменения.
6. Diff не содержит чужих и generated-файлов; документация соответствует фактическому поведению.
7. Новый долг не скрыт: отложенные проблемы имеют карточку со ссылкой и причиной отсрочки.
8. PR получил независимое ревью, а карточка переведена из «в работе» в конечный статус.

## 7. Порядок внедрения

1. Разделить текущую смешанную работу на ревьюибельные PR и зафиксировать чистый baseline на `main`.
2. Добавить `pr-fast` и `pr-blender`, сделать обязательный набор без skip и защитить `main`.
3. Ввести worktree-правило для параллельных агентов и шаблон PR с критериями/проверками.
4. Исполнить блокирующие задачи из [реестра техдолга](tech-debt/README.md) до следующего крупного расширения DSL.
5. Добавить Godot smoke и scheduled-full после закрепления версий и стабильного набора сцен.
6. Раз в итерацию просматривать открытый техдолг: закрывать доказанным изменением, понижать/отклонять устаревшее, не копить дубликаты.
