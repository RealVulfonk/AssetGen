## Методика и ограничения измерений

Использованы история выполненных команд, [журнал ассета](../asset-work-log.md#2026-11-24--модульная-стена-и-тестовый-угловой-префаб), отчёты моделей и текстур, размеры файлов и их `mtime`.

- Точных счётчиков входных/выходных токенов и длительности tool calls в доступной истории нет. Поэтому точные количества токенов, секунды всей задачи и проценты экономии не заявляются.
- Оценка токенов относительная. Прокси-метрики: объём выведенных JSON, число созданных вручную файлов, количество изображений и повторных запусков.
- Для последовательных циклов `model` и `texture` разница `mtime` соседних отчётов приближает длительность следующего ассета вместе с запуском процесса. Это не чистое время Blender. Начало первой стадии не записано, поэтому её длительность не восстанавливается.
- Два запуска Godot через GUI-исполняемый файл не дали наблюдаемого журнала или выходов и не считаются успешной проверкой. Фактические результаты подтверждены последующими запусками через `_console.exe`.

## Как был собран угловой префаб

Исходники остались четырьмя независимыми текстурированными `_godot.glb`: тело стены, колонна, горизонтальная балка и прямой брус для раскосины. [wall_corner_01.tscn](../../out/exteriors/wall_core_01/prefabs/architecture/walls/wall_corner_01.tscn) только инстанцирует их и не объединяет геометрию.

```text
WallCorner01
├── WallX, position (-1, 0, 0)
│   ├── Core
│   ├── TopBeam / MiddleBeam
│   └── LeftBrace / RightBrace, rotation Z = ±45°
├── WallZ, position (0, 0, 1), rotation Y = -90°
│   ├── Core
│   ├── TopBeam / MiddleBeam
│   └── LeftBrace / RightBrace, rotation Z = ±45°
├── ColumnOuterX, position (-2, 0, 0)
├── ColumnCorner, position (0, 0, 0)
└── ColumnOuterZ, position (0, 0, 2)
```

Ключевые решения:

- Наружная сторона core смотрит в локальный `-Z` Godot; обе панели используют одинаковую локальную систему, а вторая поворачивается целиком.
- Балки стоят на внутренней стороне с центром `z=0.2`: при глубине 0,12 м они на 0,01 м утоплены в облицовку и не висят отдельно.
- Угловая колонна существует в одном экземпляре; две панели не создают дубликат на общем конце.
- Раскосины не запечены в модель: один `wall_brace_01` поворачивается на ±45° в префабе.
- Коллизии приходят из импортированных `_godot.glb`; вручную узлы `StaticBody3D` и `CollisionShape3D` не дублировались.
- Результат: 13 видимых мешей, 13 коллизий, 820 треугольников, габарит 2,36 × 2,5 × 2,46 м. Проверены наружный и внутренний ракурсы и две последовательные панели на шаге 2 м.

Это хорошая структура для теста: локальные координаты панели понятны, модули остаются самостоятельными, ссылки относительные. Повторное описание `WallX` и `WallZ` — допустимая плата за один тест, но не лучший формат для серии разных углов.

## Оптимизация по шагам

### 1. Предварительный поиск и чтение правил

**Что было сделано.** Проверены Git, навык AssetGen, журнал, README, схема, прежняя `wall_stone_01`, `pillar`, prefab skill и PBR-источники. Это предотвратило изменение чужой стены и не нужное расширение DSL.

**Потеря.** Первый широкий поиск по `docs` вернул около 23 КБ; часть карточек и больших разделов не влияла на конкретную геометрию.

**Оптимизация.** Сначала искать имена и симптомы в режиме `files_with_matches`, затем читать только найденные разделы. Для аналогичной стены достаточно: AssetGen skill, prefab skill, прежней wall-спеки, PBR-спеки, ограничений конкретных карт и журнала. Полные схемы открывать только по используемым полям. Сокращать нужно контекст, а не обязательный `git status` и запись журнала.

### 2. Планирование и журнал

**Что было хорошо.** До спек зафиксированы ориентация, pivot, размеры, способ получения независимых сторон без z-fighting и критерий Godot-проверки.

**Оптимизация.** Сохранить текущий порядок. Промежуточные комментарии оставлять короткими, а численные результаты не дублировать в нескольких местах: подробности хранятся в отчёте, журнал ссылается на него. Это вторичная экономия, не повод убирать обязательные решения и ограничения.

### 3. Создание спек

**Что было хорошо.** Четыре `new` и параллельная запись восьми JSON; каждый ассет прошёл схему с первого раза. Не создано новых полей и зависимостей.

**Потеря.** PBR-настройки повторяются в `stone_outer`, `stone_inner`, `stone_edge` и колонне. Это умеренный объём ручной работы, но высокий риск расхождения параметров при серии стен.

**Оптимизация сейчас.** Для одной партии оставить явные JSON и общий authoring-checklist: одинаковые `brightness/contrast/ao/edge/roughness`, имена трёх карт и физический `tile_size`.

**Не делать сейчас.** Не вводить наследование материалов или новый генератор ради одной стены. Если появится серия однотипных стен, отдельной нерутинной задачей можно создать генератор спек со схемой, тестами и контролем старой спеки.

### 4. Validate и model

**Что было хорошо.** Все спеки валидированы до Blender; циклы останавливались при ошибке. Каждая модель собрана один раз, отчёты без warnings.

**Оптимизация.** Сохранить последовательный цикл: общий `out/` и блокировка сборки не делают параллельные Blender бесплатными или безопасными. Сначала проверять все спеки, затем собирать всю партию без интерактивных пауз. Полные JSON можно не возвращать в разговор: существующие файлы отчётов читать выборочно по `status`, `warnings`, `tris`, `dimensions`, `materials`.

**Возможное изменение инструмента.** Отдельной задачей добавить CLI `--quiet`/`--summary`; сейчас таких флагов нет, поэтому нельзя просто рекомендовать их как существующую команду.

### 5. Texture — главный кандидат на экономию

**Что было хорошо.** Все текстуры получены с первого bake, PBR-карты согласованы, ошибочной перекраски и повторных bake не было.

**Потери.** `--lighting-preview` запрошен для всех четырёх ассетов, включая два простых деревянных бруса. Полные настройки материалов и пути выведены в контекст четыре раза.

**Оптимизация без потери приёмки.**

- Для балки и раскосины использовать обычный `texture --no-copy`; их проверять на итоговом угле, а не отдельным Godot A/B.
- Lighting preview оставить для core, если нужно проверить две стороны; колонну и дерево допустимо принять в составе угла.
- Итоговый corner/repeat рендер обязателен и не заменяется отдельными превью модулей.
- Не уменьшать 512 px и не убирать Normal/Roughness только ради скорости без A/B-доказательства сохранения качества.
- После bake выводить компактную сводку; полный JSON читать только при warning или несоответствии.

Наибольший выигрыш здесь даёт не параллелизм, а меньшее количество вспомогательных Godot-рендеров и меньший вывод в контекст.

### 6. Визуальный контроль

**Потеря.** Отдельно просматривались iso/front/lighting разных модулей и исходные карты; одно изображение исходника было прочитано повторно. Каждое изображение добавляет существенный контекст.

**Оптимизация.** Делать один contact sheet четырёх модулей с одинаковой камерой, затем только `preview_corner.png` и `preview_repeat.png`. Front/back нужны обязательно для этой стены, top — для угла и пересвеченных торцов; остальные ракурсы открывать по подозрительному месту. Контактный лист должен быть verification-выходом, а не новым production-ассетом.

### 7. Структура префаба

**Для одного теста.** Текущий `.tscn` можно сохранить: он короткий, явный и уже проверен. Переписывание ради уменьшения числа строк не даст измеримой выгоды.

**Для дальнейшего переиспользования.** Вынести `wall_framed_01.tscn`: core + две балки + две раскосины. Тогда угол содержит только два экземпляра framed panel и три колонны:

```text
WallCorner01
├── FramedX, (-1, 0, 0)
├── FramedZ, (0, 0, 1), rotation Y = -90°
├── ColumnOuterX
├── ColumnCorner
└── ColumnOuterZ
```

Плюс — координаты и повороты балок существуют в одном месте. Минус — дополнительная сцена и уровень зависимости. Поэтому framed panel оправдан при реальном повторном использовании, а не автоматически для каждого теста.

**Следующий уровень автоматизации.** Если появятся разные длины, углы и варианты каркаса, декларативный manifest с размерами/pivot/ориентацией и детерминированный `tools/create_wall_prefab.py` устранит ручной расчёт. Потребуются отдельная карточка, схема manifest, тесты относительных путей, поворотов, коллизий и контрольный Godot-импорт.

### 8. Изолированный Godot-проект

**Что было хорошо.** Относительная структура GLB/`.tscn` воспроизведена, штатный импорт выполнен, production-файлы не загрязнены `.godot`.

**Потеря.** Вручную созданы каталоги и скопированы четыре GLB и пять сцен. Это повторяемая механическая работа.

**Оптимизация без кода.** Сохранять список входов одной командой копирования и использовать тот же корень verification для corner и repeat, как уже сделано во втором тесте.

**При повторении задач.** Общий harness должен принимать список ассетов и prefab path, копировать только `_godot.glb` и нужные `.tscn`, сохранять относительные пути, затем запускать import и проверку. Не использовать symlink как обязательное решение на Windows и не ставить `project.godot` в общий production `out/`.

### 9. GDScript и запуск Godot — главная избегаемая потеря

**Фактические проблемы.** Два вызова через GUI executable не дали результата; `Vector3.max_component()` оказался недоступен; вывод `Variant` через `max()` был остановлен warning-as-error. После исправлений проверка прошла. Свет потребовал второго успешного рендера.

**Оптимизация следующего запуска.**

1. До написания проверки зафиксировать путь к `Godot_v..._console.exe`; проект и скрипт передавать абсолютными путями.
2. Перед графическим рендером выполнять `--headless --check-only --script <absolute.gd>`; это отделяет parse/type errors от импорта и рендера.
3. Использовать уже проверенные идиомы из `tests/verify_pbr_import.gd`, явно типизировать значения, получаемые из Variant.
4. Объединить corner и repeat в один сценарий с общими функциями света, камеры, окружения и сохранения кадров. Сейчас вторая половина `verify_repeat.gd` повторяет corner-скрипт.
5. Начинать с нейтрального существующего lighting rig и маленького пробного кадра; финальный 768 px сохранять после проверки экспозиции.
6. Для одиночного префаба оставить явные ожидаемые 13 meshes/820 triangles/bounds. Для серии — передавать ожидания manifest-файлом, а не размножать hard-coded скрипты.

### 10. Финальная проверка и документация

**Что было хорошо.** Проверены две bare-панели, отсутствие изменений старой стены, `git diff --check`, ссылки и отчёты. Это дешёвая страховка от ложного «готово».

**Оптимизация.** Сохранить эти проверки. Не повторять model/texture для документационной правки. Журнал может ссылаться на machine-readable Godot-отчёт вместо повторения всех полей, но обязан сохранить команды, фактический исход и ограничения.

## Приоритетный план для следующей аналогичной партии

### Без изменения репозитория

1. Запускать только необходимые lighting previews; дерево проверять в составе угла.
2. Сразу использовать Godot console и `--check-only` перед рендером.
3. Один verification-проект и один скрипт для corner + repeat + двух сторон.
4. Один contact sheet модулей вместо серии отдельных изображений.
5. Читать компактные поля отчётов вместо возврата всех JSON в контекст.

### Небольшое документационное улучшение

Дополнить prefab workflow правилами выбора console executable, проверки GDScript до рендера и порогом, когда нужен framed panel. Это отдельное изменение инструкции, в текущую аналитику не входит.

### Инструментарий только после подтверждённого повторения

- CLI compact output для model/texture.
- Детерминированный генератор составных wall-префабов по manifest.
- Универсальный Godot verification harness с копированием, ожиданиями и контактными листами.

Для каждого пункта нужен текущий потребитель и отдельная нерутинная карточка. Не оправданы сейчас: параллельные Blender в одном `out/`, слияние модулей в один меш, удаление PBR или Godot-проверок, новый DSL ради повторяющихся пяти полей.

## Как измерить следующий прогон честно
