# TD-008 · Детерминизм двух независимых чистых сборок

Приоритет — P1. Тип — tests/reliability. Объём — M.
Статус — предложено. Доказательство — подтверждено границами текущего теста.

## Проблема и доказательство

[`verify_determinism.py:28-35`](../../tests/verify_determinism.py#L28-L35) дважды открывает один `.blend` в одном Blender-процессе и вызывает `texture.main()`. [`verify_determinism.py:46-59`](../../tests/verify_determinism.py#L46-L59) сравнивает только пиксели albedo и нормализованные texture reports.

Это полезный bake smoke, но он не проверяет повторное построение модели, RNG после mirror/array, UV, геометрию, GLB и независимость процессов.

## Сценарий влияния

Изменение порядка итерации или состояние сцены делает чистые CLI-сборки разными, а существующий тест остаётся зелёным, потому что обе итерации начинаются с одного готового входа.

## Границы

Сохранить текущий тест как быстрый численный bake check. Не требовать побайтового GLB без предварительной проверки стабильности экспортёра и не сравнивать результаты разных версий Blender как один golden.

## Минимальный план

1. Выполнить два независимых CLI model+texture run в разных временных каталогах на закреплённой версии Blender.
2. Сравнить albedo hash, нормализованные reports, состав/иерархию GLB, transforms, материалы, collision, UV и геометрию с устойчивой канонической сортировкой.
3. Переиспользовать reference build helpers; не создавать отдельный копирующий runner.
4. Запускать на небольшом контрольном наборе, включая jitter+mirror и cutout.

## Приёмка

- Два одинаковых чистых прогона дают одинаковый albedo и нормализованную модель/GLB-семантику.
- Намеренное изменение RNG или transform обнаруживается тестом.
- Пути, timestamps и порядок служебных JSON-полей не дают ложных различий.
- В отчёте видны версии инструментов и входные digest из TD-002.
